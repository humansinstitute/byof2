# NStack context for interview and build agents

Generated BYO apps use NStack as their normal persistence architecture. Postgres-backed JSON collections hold app records; S3-compatible object storage holds binary files. Agents use the scoped `createFreedomData` SDK, never SQL, S3 credentials or an arbitrary backend. Core BYO conversations/designs remain in the existing app database; this guidance does not migrate them.

Every newly enqueued interview **and** implementation job receives a bounded `context.storage` snapshot generated from the app's actual saved/runtime NStack settings. It records contract version1, settings revision, connection mode/readiness, JSON/file/policy/anonymous-read availability, independent workspace membership requirements, SDK/manifest contract, namespace rules and real SDK quotas. No endpoint, identity, workspace label, token or credential is copied. Implementation jobs additionally receive the existing SDK source and public app origin. The captured facts are immutable job context, not a storage grant: operations still enforce current installation, actor, namespace, revision and permission checks.

Interview prepare v6 and builder prepare v5 explicitly explain this platform contract. Interviewing asks about audience, shared/private visibility and posting/moderation behavior rather than making the participant provision a backend or provide credentials. Building packages the SDK and `byo-data.json` version1 permission request. Exact-version installation still needs an administrator. The agent must preserve requested functionality while distinguishing it from enabled capabilities and report concrete prerequisites when unavailable.

- A shared event guestbook needs `shared` JSON collections and managed delegation. Private collections are per signer and cannot implement cross-user sharing.
- Event photos use `filePut`/`fileGet` in an approved collection; JSON records link logical files to captions/messages. File access follows its collection policy. Encoding photos in JSON or persisting them in localStorage/SQLite is not a fallback.
- `public` collections permit anonymous reads only for an exposed exact version; only admins write. A participant-posted guestbook normally uses `shared`, not public writes.
- Browser-authorized mode supports private JSON only, requires every signer to independently belong to the selected NStack workspace, and does not support shared/public/anonymous operations or files. BYO project membership alone is insufficient.
- Native interview image attachments are private design reference evidence. They do not activate event-photo storage for generated apps.
- Files require a separate approved managed object-storage binding. When disabled, agents must show/report an honest unavailable state and preserve unsent input in memory, without claiming remote success.

The actual SDK maximums are16collections,100records per collection,1,000mutation revisions,64KiB per JSON value,256KiB per file and100records per page; manifests may narrow them. Native interview image limits are unrelated.

New sources are `pipelines/interview.v6.json`/`byofreedom.prepareInterview.v6` and `pipelines/builder.v6.json`/`byofreedom.prepareBuilder.v5`. Native conversation keys/profiles and the builder's `byofreedom.agentPublish.v4` publication and `finishBuilder.v2` handlers stay unchanged. The image composer supports reviewed interviewv5 andv6 workflows when scoped tools and pipeline config are enabled. Existing versioned functions/definitions are preserved; deploy by installing the new files, registering fresh exact-definition/composition grants and changing both app configs/workflow versions. Source preparation does not activate pipelines, shared delegation or file storage. Never repoint old in-flight/uncertain jobs to a new grant.
