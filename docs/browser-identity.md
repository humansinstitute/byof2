# Remembered browser identity

BYO Freedom restores the saved signer before authenticated routing. Closing/reopening the same browser profile at the **same origin** signs back into the same account without a password prompt. Direct design/app routes and pending invitations survive login. Account roles, membership and design ownership still come from the server.

The previous client already attempted `/api/me` when `byo-freedom.signer.v1` existed. Normal browser shutdown does not normally clear localStorage. Its return-state defect was treating a missing signer marker as no login even when the browser key remained; explicit signout also removed that marker, making these states indistinguishable. Browser creation and import also used direct, unverified plaintext writes without cross-tab coordination. This change repairs those paths; it does not establish which browser/profile/origin Pete used during the reported incident.

## Storage and migration

`public/identity-vault.ts` stores one versioned envelope in the `byo-freedom.identity.v2` IndexedDB database. It contains a structured-cloned **nonextractable** AES-256-GCM CryptoKey, a fresh random 96-bit IV, authenticated ciphertext, and the public key. Additional authenticated data binds the format/version and exact public key. Decryption validates the secp256k1 secret against that public key.

The legacy `byo-freedom.identity.v1` localStorage hex secret is migrated under a same-origin Web Lock. The vault writes with strict transaction durability, reads the committed envelope back, decrypts it and checks the exact secret/public key before removing the plaintext legacy entry. Failure retains the original data. An existing encrypted envelope is verified first; conflicting legacy/encrypted identities are preserved and block browser login. Atomic IndexedDB `add` and the lock prevent concurrent creation or migration from overwriting the first saved identity. No plaintext fallback or volatile account is used if saving fails. WebCrypto and IndexedDB/CryptoKey cloning are required. Creation/import/migration additionally require Web Locks; existing encrypted identities can be read without Web Locks; an external Nostr signer remains available.

`public/browser-identity.ts` initializes once before routing, remembers signer choice, and signs/decrypts/exports using a transient decrypted secret. It never caches the plaintext secret. Byte arrays under its control are cleared after use; JavaScript and cryptographic libraries cannot promise complete memory erasure. Recovery exports intentionally contain the private key and must be kept private; they are never uploaded by the recovery flow.

Explicit **Sign out** saves a separate marker without deleting the identity or signer choice. Returning stays signed out and offers **Continue** or extension reconnection. A missing signer marker with a valid vault/legacy key restores browser mode unless the explicit signout marker exists. Historical signouts from the old client cannot be distinguished from accidental marker loss, so a legacy key with no marker restores automatically once. A remembered extension is never replaced automatically by a browser identity when absent, delayed or locked. Extension injection is given a short startup grace period, then the user can reconnect/retry.

Invalid legacy secrets, corrupt ciphertext, missing wrapping keys, unsupported/denied storage and crypto failures show recovery guidance and preserve evidence. They never mint replacement identities. Importing a different recovery key over an existing valid browser identity is refused: use a separate browser profile for that account. For corrupt storage, retain the affected profile/data and restore a known recovery key in a fresh profile. If a valid legacy key remains after a migration failure, the entry page offers an explicit local recovery export even when encrypted storage cannot be opened. No automatic destructive repair is offered.

## Limits and recovery

Encryption reduces plaintext-at-rest exposure. It is **not** an OS keychain or hardware isolation guarantee. Same-origin compromised JavaScript can use the persisted CryptoKey and decrypt/sign; local device compromise can also defeat browser protections. A usable no-password return identity necessarily grants the origin signing capability.

The browser is asked for persistent storage best effort after saving. It can refuse; users or the browser can still clear/evict storage. Private browsing is not durable beyond that private session. Export a recovery key for another device/profile or cleared storage. No server copy, cookie session or external vault service is introduced.

`https://byof.otherstuff.ai` and `https://byo-freedom.b.otherstuff.ai` have separate browser stores, including their wrapping keys and signer permissions. Visiting a new origin cannot discover an identity on the other origin. No key transfer, redirect-based identity replacement, URL secret or cross-origin message bridge is used. On the other origin explicitly import the original recovery key (or reconnect the same extension identity) to access the same server account. An empty origin offers explicit creation, but creating there produces a different account; it is not migration. Returning to the original origin with its original profile still restores its saved account.

## Local validation

After `bun run build`, run `bun integration/identity-browser.ts`. It launches and completely closes real persistent Chrome contexts/processes, reopens the same userDataDir, and uses an isolated in-process HTTP app and SQLite fixture. It covers exact identity/profile/membership/design retention, desktop/phone viewports, verified migration with/without signer marker, signout/continue, signatures/NIP44, encrypted storage, failures and races. Screenshots and nonsecret results go only to verified ignored `tmp/docs/handoffs/identity-vault/`. Browser profile directories are temporary and removed after the run. Phone coverage is viewport emulation, not a physical device claim.

Run `bun integration/invite-browser.ts` for real browser invitation creation/import/extension regressions. These are local fixture checks, not deployed acceptance. `integration/identity-hosted-browser.ts` is an opt-in hosted UI check against an explicitly supplied owned isolated project; the deployment manager runs it after activation. Never point it at a personal account/profile or a project without fixture-write authorization.
