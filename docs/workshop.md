# First-time workshop journey

Open a project invitation at `/ic=<code>` on the origin you intend to keep using. Before login, `/api/invitation?code=<code>` returns only the active workshop title. New participants enter a first name or nickname and Continue. The browser identity uses the existing encrypted durable vault; the name and authenticated membership save before the project opens. Pending name/invitation survive a failed request and reload. Existing identity, extension and recovery controls remain under “Use an existing identity”. Origin, private-browsing and storage-loss limits are unchanged; see [browser-identity.md](browser-identity.md).

Every project shows retirement, Bitcoin will, inflation/savings and hair-price idea cards, plus own-idea and help-finding-an-idea options. Idea cards contain no fabricated calculator, financial advice or legal guide. Only an explicitly selected tested static package gets Try it. Reference previews block live data and remote dependencies, so organisers should verify each actual example in this sandbox before inviting participants.

Administrators choose **More → Choose workshop examples** in the design-conversations project view. Select a tested version, preview/review its exact code, paste the reviewed starting document and approve sharing both. The signed `PATCH /api/projects/:id/workshop` takes `{starterId, versionId, document, confirmPackage:true, expectedRevision, requestId}`. Use the revision from the member GET and retain the same request ID and payload on uncertain retries; stale selections conflict and exact retries create no duplicate share. Starter IDs are `retirement`, `bitcoin-will`, `inflation`, `hair`. Empty `versionId` makes that card an idea starter again; the explicitly approved library share can separately be revoked using Manage shared versions. No private source document is copied automatically. A legal guide needs an agreed jurisdiction and qualified review; calculator assumptions and claims need the organiser’s review.

The implementation creates an ordinary approved artefact-library share and stores its selected ID plus the approved starting document in a `workshopStarter` record. Member-only `GET /api/projects/:id/workshop` resolves active shares through existing ACLs. Revoked, deleted or archived sources stop new preview/import access. Existing independent copies remain. `POST` takes `{starterId, requestId}` and idempotently creates a participant-owned design/conversation, an approved-document snapshot if selected, and existing imported-package provenance. It never mutates source records, copies chats/private images, inherits data installations or queues a build. Imported material remains untrusted reference, not confirmed participant requirements.

New workshop designs have compact Your idea / Shape it / Your result stages and a conversational opening with editable tappable suggestions. Review your design opens the latest saved document. Unsent text/images or historical selection must be resolved first; a changed snapshot rejects confirmation. “Looks right — request organiser” invokes the existing idempotent waiting-build endpoint. Participants cannot execute host builds: the server gate is unchanged. Organisers find the linked request under the participant’s design and can explicitly handle that build conversation. There is no new notification service or automatic processing.

A result appears only from a registered version. Try it opens its actual sandboxed package full screen; Make a change returns to the same design. Labels distinguish private preview from project-site publication. Organisers can see participant work; participants cannot see each other’s private designs or requests. Website publication, sharing, data installations and advanced historical build tools remain administrator actions. Version history is under More in the participant workspace. Draft storage and ongoing-job polling reuse the existing recovery paths; progress comes only from saved runtime state.

## Activation and validation

This source change adds JSON records to the existing generic SQLite store, with no SQL schema migration, storage activation or runtime-permission change. The additive `prepare-interview.v8.ts` and `interview.v9.json` carry app-owned bounded workshop presentation instructions through `context.workshop`, outside participant evidence. They retain the native conversation key, scoped tools and reply-first `finishInterview.v5`; existing installed workflow versions remain unchanged. The deployment manager must install the new immutable function/definition and issue its fresh exact-composition grant, then set `INTERVIEW_WORKFLOW_VERSION=interview-v9` and its matching `INTERVIEW_PIPELINE_CONFIG`/server-only credential. Preserve the original v8 grant/config for in-flight recovery; never repoint old jobs. No Autopilot code change or restart is required. Back up the persistent database as usual before the BYO release. Preserve the existing volume, origins and every unrelated configuration value; only the reviewed `APP_VERSION` and exact interview v9 workflow/config/credential fields change. Configure the real starter through the normal signed admin API after deployment, then verify the exact origin’s fresh-browser invitation and real native interview. Signed public activity accepts the v8/v9 interview definitions under the same exact job/run/turn checks. Source tests do not establish live activation or native-model acceptance.

Run the regular frozen install, type check, Docker-enabled tests and build, then `bun integration/workshop-journey-browser.ts`. That runner uses an isolated in-memory database, real signed HTTP and Chrome at phone/desktop viewports, with synthetic completed interview and administrator result registrations. It verifies actual counter interactions, name-only entry, personal copying, privacy, reload/reconnect and no participant host jobs. Evidence goes only to verified ignored `tmp/docs/handoffs/workshop-journey/`. This is viewport emulation, not physical-device keyboard or lock/unlock certification. Existing invitation, identity and reply-first runners remain relevant regressions.

The summary checkpoint keeps its heading and both decision buttons outside the scrolling design document. Its bounded dialog supports small phone viewports; only the document scrolls. The notice distinguishes the private conversation from the result, which an organiser may explicitly share or publish.
